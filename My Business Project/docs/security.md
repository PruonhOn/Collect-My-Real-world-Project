# Security

## 1. Authentication

| Flow | Mechanism |
| --- | --- |
| Browser session | Laravel Sanctum personal access tokens (`Authorization: Bearer <token>`) |
| Token lifetime | Configurable in `config/sanctum.php` (`expiration`), 0 = non-expiring |
| Password storage | `bcrypt` (Laravel default `Hash` driver) |
| Password reset | Signed, single-use token, `password_reset_tokens` table, throttled endpoint |
| Email verification | Signed URL `/api/v1/email/verify/{id}/{hash}` + `email_verified_at` |
| Invitation | 48 character random token in `business_memberships.invite_token`, single use |
| External API | Business-scoped API tokens with abilities, hash-only storage |

The SPA stores the Sanctum token in `localStorage["my_business.token"]`. If the
project is later served from a domain with a stricter threat model, swap the
storage to an HttpOnly cookie with Sanctum's SPA mode — the API contract does
not change.

### Login protection

- `/auth/login` and `/auth/register` are rate limited by the `throttle:auth`
  limiter.
- `/auth/forgot-password` and `/auth/reset-password` are throttled as well.
- Login responses never disclose whether an email exists.

## 2. Authorisation

| Layer | Mechanism |
| --- | --- |
| Platform admin | `SuperAdminMiddleware` checks `users.is_super_admin` |
| Business scope | `EnsureBusinessContext` requires an active membership (ownership always passes) |
| Role checks | `BusinessController::assertManager()` (owner/admin) for profile and settings |
| Entitlements | `EnsureFeatureEnabled` rejects with `403` + `upgrade_required: true` |
| Resource ownership | Controllers verify `business_id` before mutation (for example `TeamController::update`) |

Rules that are enforced in code and covered by tests:

- A staff member cannot manage members, settings or billing.
- A business owner cannot be demoted or removed through the team API; ownership
  is transferred through a dedicated workflow.
- The owner cannot delete their own account, and an administrator cannot
  remove their own super-admin rights.
- A suspended business is blocked from using the workspace.

## 3. Tenant isolation

Tenant isolation is enforced on three levels, so a single mistake is not
enough to leak data:

1. **Request level** — `EnsureBusinessContext` resolves the tenant from the
   `X-Business-Id` header and refuses to continue without a valid membership.
2. **Query level** — `BusinessScope` adds the `business_id` constraint to every
   tenant-owned model.
3. **Resource level** — mutating endpoints re-check that the loaded record
   belongs to the current business before writing.

`tests/Feature/TenantIsolationTest.php` exercises the boundary from outside:
ids from another tenant produce `404`, never `403`-with-data and never `200`.

The `X-Business-Id` header is a *hint*, not an authority: it selects the
tenant, it never grants access.

## 4. API tokens

`ApiTokenService` issues a token with:

- a 64 character random secret; only its SHA-256 hash is stored,
- an explicit ability list (`products:read`, `products:write`, `customers:read`,
  `customers:write`, `orders:read`, `orders:write`),
- an optional expiry (1–365 days),
- a business scope: the token can only ever reach the business that issued it,
  never more than the issuing user could reach.

External routes live under `/api/v1/external` and are protected by the
`api.token` middleware plus a per-ability `api.token:<resource>:<action>`
middleware. A token can never widen the access of its creator.

## 5. Webhooks

| Provider | Endpoint | Verification |
| --- | --- | --- |
| Stripe | `POST /api/v1/webhooks/stripe` | Signature header `Stripe-Signature` |
| Bakong | `POST /api/v1/webhooks/bakong` | Shared secret / payload signature |
| ABA Payway | `POST /api/v1/webhooks/aba` | `X-Signature` hash of the payload |
| Fake (dev only) | `POST /api/v1/webhooks/fake` | `X-Fake-Signature: fake-webhook-secret` |

The fake webhook route is registered **only** in the `local` and `testing`
environments. Every provider event is recorded in `payment_webhook_events`
with a unique `event_id`; a duplicate delivery is ignored, so a replayed
callback can never grant a subscription twice.

## 6. Input handling

- All writes go through `validate()` with explicit rules; no mass assignment
  of unvalidated input.
- Selects use `Rule::in(...)` / `Rule::exists(...)` instead of free strings.
- The frontend validates with the same rules through `zod`, but the server is
  the only authority.
- HTML output is rendered by React, which escapes by default. Email bodies use
  Blade with `{{ }}` (escaped) — never `{!! !!}`.
- SQL injection is prevented by the query builder; no raw SQL with user input
  exists in the request path.

## 7. Secrets

| Secret | Where it lives |
| --- | --- |
| `APP_KEY` | `.env`, generated by `php artisan key:generate` |
| Database credentials | `.env` / injected environment variables |
| `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` | `.env`, never committed |
| `BAKONG_SECRET_KEY`, `ABA_PRIVATE_KEY`, `ABA_IPN_HASH` | `.env`, never committed |
| Mail credentials | `.env` |

`.env` is excluded from version control; `.env.example` documents every key
without values. Rotate any secret that has been exposed in a log, a commit or
a chat message.

## 8. Rate limiting and abuse protection

| Scope | Limiter |
| --- | --- |
| Login / registration | `throttle:auth` |
| Password reset | `throttle:auth` |
| Business creation | tenant limit `max_businesses` |
| Catalogue / customer / member creation | plan limit `max_*` |
| Checkout | gateway rate limits + plan status |

Plan limits are enforced server side by `FeatureGate::checkLimit()`, not by the
UI. Exceeding a limit returns `422` with `upgrade_required: true`.

## 9. Logging and audit

- Application log: `storage/logs/laravel.log`, rotate daily, keep 14 days.
- Business mutations are recorded in `business_activity_logs`.
- Administrative mutations are recorded in `admin_audit_logs` with actor,
  action, reason, old and new values, IP and user agent.
- Never log credentials, tokens or full request bodies of authentication
  endpoints.

## 10. Hardening checklist

Before going to production:

- [ ] `APP_ENV=production`, `APP_DEBUG=false`
- [ ] `APP_KEY` generated and unique
- [ ] HTTPS enforced, HSTS enabled at the edge
- [ ] Database user restricted to the application schema
- [ ] `php artisan config:cache && php artisan route:cache && php artisan view:cache`
- [ ] Queue worker and scheduler running (see [deployment.md](deployment.md))
- [ ] Automated backups verified (see [backup-recovery.md](backup-recovery.md))
- [ ] Real payment gateway configured and webhook secret set
- [ ] `BILLING_DEFAULT_GATEWAY` switched away from `fake`
- [ ] Log rotation and disk alerting configured
